# The three L2 fixture repositories are vendored in this repository, not forked on GitHub

[S2c](https://github.com/lbacik/coding-agent/issues/18) needed three real repositories — one per language — that bootstrap and validate for real inside the image, each carrying a committed `docs/agents/project-profile.yml` at `schema: 2`. Where they live and how they are pinned is the one open choice the issue calls out and asks to be recorded.

They live under `fixtures/l2/{python,php,typescript}/` in this repository, committed alongside the `project-profile.yml` each one needs. The pin is this repository's own commit — nothing external to track.

## Considered options

**Fork three real open-source repositories on GitHub and add a profile to each.** Rejected. This slice explicitly excludes GitHub ("Not in this slice: Attempts, the Run Ledger, GitHub" — S2c's own scope) — the three fixtures have no need to be reachable repositories at all. Forking real projects onto the Agent Identity's or a maintainer's account only to append one file is also a public, hard-to-reverse action out of proportion to what the issue asks for, and it puts three toolchain versions' worth of upstream drift outside this repository's control.

**Clone pinned upstream repositories at build time (the Skill Bundle's own pattern) and overlay a profile.** Rejected. It would need a profile overlay step with nowhere obviously right to live, buys nothing L2-1/L2-2 need, and reintroduces exactly the network dependency and drift the first option has, just moved into the Dockerfile.

**Vendor real, working, minimal projects in this repository.** Accepted. "Real" is what the issue is actually protecting against — "a toy will pass a parser and teach nothing about a bootstrap" — and that means a genuine `uv sync`/`composer install`/`pnpm install`, a genuine `pytest`/`PHPUnit`/`vitest` run, and genuine JUnit XML from that run, exercised through a real `CommandRunner` rather than a fake one. Nothing about that requires the source tree itself to be an existing OSS project; S2b already covers the harness's decision logic against fakes in `tests/test_validate.py`, so what S2c owes is real toolchains, not new coverage of that logic.

## What each fixture carries

Each fixture has two test files (so `test_targeted` can be told apart from `test_all`) and one deliberately red test in the second file, so the Delivery Snapshot's evidence has a real executed count and a real named failure to report, not just a clean pass. The three profile traits the issue calls out are spread one-per-fixture rather than duplicated:

- **Python** (`fixtures/l2/python/`): `checks: none` at the fixture root.
- **PHP** (`fixtures/l2/php/`): `working_directory: app` — the profile lives at the fixture root, the project one level under it — and a declared `service`, reachability-probed for real by `scripts/verify-l2-fixtures.sh` against a real listener via `check_service.py`.
- **TypeScript** (`fixtures/l2/typescript/`): a real `checks` entry (`tsc --noEmit`).

## Consequences

**Fixtures and `scripts/verify-l2-fixtures.sh` are a verification asset, not image payload.** They are never `COPY`'d into the Dockerfile; `verify-l2-fixtures.sh` builds the image and bind-mounts each fixture read-only into a container from it, mirroring how `scripts/verify-image.sh` already proves S1's build without changing what the image ships.

**Each fixture's lockfile is generated with this image's own pinned toolchain, not the author's workstation.** `pnpm-lock.yaml` in particular records platform-specific optional dependencies (native `esbuild`/`rollup` binaries) at generation time; a lockfile made on a developer's machine can silently omit the binary the image's own platform needs. `fixtures/l2/typescript/pnpm-lock.yaml` was generated by running `pnpm install` inside a container built from this Dockerfile, and any future dependency change to that fixture must be relocked the same way.

**A real Target Repository's `docs/agents/project-profile.yml` is unaffected.** These fixtures prove the harness against real toolchains; they say nothing about what a real Target Repository from [#12](https://github.com/lbacik/coding-agent/issues/12) declares in its own profile, which stays a decision for that repository's own maintainers.
