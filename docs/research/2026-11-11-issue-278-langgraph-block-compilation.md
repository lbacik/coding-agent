# LangGraph primitives for declarative Workflow Blocks

Research for [What LangGraph primitives can execute a validated YAML block graph without generated code?](https://github.com/lbacik/coding-agent/issues/278), under [Design: declarative block workflows compiled from YAML to LangGraph](https://github.com/lbacik/coding-agent/issues/276).

## Scope and evidence

This note establishes framework facts and their implications. It selects no new runtime policy or YAML contract. The owner-confirmed first release has one entry point, conditional choice of one successor and bounded loops. Workflow-level fan-out/fan-in and author-defined nested Workflows are deferred; existing model-invoked Sub-agents are a separate concern.

## A data definition can be compiled directly

LangGraph accepts Python callables registered with explicit names. A compiler can iterate normalized block declarations, obtain a callable from a trusted executor registry, call `add_node`, connect `START` to the selected entry, add event routers with explicit `path_map` dictionaries and connect terminal nodes to `END`. The result is compiled in memory. No generated Python module, `eval`, dynamic import from YAML or framework extension is needed. Runtime context can supply dependencies independently of graph state. [Graph API overview](https://docs.langchain.com/oss/python/langgraph/graph-api), [build checklist](https://docs.langchain.com/oss/python/langgraph/use-graph-api).

This is an application/compiler inference from those interfaces, not a claim that LangGraph includes a coding-agent YAML loader. The existing Worker already builds and compiles a graph programmatically with `checkpointer=None`, but selects its eleven nodes and their order from code. A new compiler can reuse that construction mechanism; deciding which lifecycle operations are configurable remains an owner decision. [Existing graph builder](https://github.com/lbacik/coding-agent/blob/815de8c3358e0d02b1f84260ab91c78b79b7f931/src/coding_agent/runtime/graph/attempt.py#L3693).

## Successors, loops and compilation checks

A conditional path function may return one destination or multiple destinations. Repeated ordinary outgoing edges also permit multiple successors. Therefore the first-release promise of choosing one successor must be enforced by the compiler/router. An explicit event-to-node `path_map` both makes destinations inspectable and avoids treating a model-supplied string as an arbitrary node name. A result absent from that map fails during branch evaluation; the product must classify that error deliberately. The `destinations` argument for a `Command`-returning node describes rendering, not an execution allowlist. [Pinned branch implementation](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/graph/_branch.py#L192), [control-flow documentation](https://docs.langchain.com/oss/python/langgraph/graph-api-control-flow).

The inspected `StateGraph.validate` verifies edge sources and known targets, declared conditional destinations, existence of an entry edge and named interrupt nodes. `add_node` also rejects duplicate/reserved names. It does **not** require exactly one entry, traverse reachability, prove any path reaches `END`, reject unbounded cycles, validate event coverage or check coding-agent input/output contracts. Consequently a structurally compilable graph can still violate the desired Workflow contract. [Pinned builder and validation](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/graph/state.py#L1129).

The YAML validation layer must independently check the chosen rules for identifiers, references, executor/model/skill availability, reachable blocks, terminal declarations, event coverage, input/output mappings and bounded cycles. Successful LangGraph compilation is an additional check, not a replacement. Whether unreachable declarations are rejected or merely diagnosed is still policy to decide.

`recursion_limit` is a framework execution-step ceiling, not a per-block visit count, token meter or dollar budget. Exceeding it raises `GraphRecursionError`. Splitting one product block into several internal nodes changes the relationship between framework steps and product visits. Product loop counters and the final classification therefore need their own semantics; the framework limit can remain an independent backstop. [Recursion-limit documentation](https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT), [pinned execution loop](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/pregel/main.py#L3000).

## Conversation and data isolation

A parent node can invoke a compiled subgraph with a different state schema, mapping explicit inputs into a private agent conversation and mapping only its result back. This permits one configurable block to contain an internal model/tool loop without exposing nested Workflows in YAML. It also allows a fresh conversation on each visit, if that is the chosen contract. Whether a new visit restores any state must be specified, not inferred from the same block ID. [Subgraph communication](https://docs.langchain.com/oss/python/langgraph/use-subgraphs).

Graph nodes return partial state updates. Channels overwrite by default; reducers define alternative merge behavior. A mapping returned for a field is not automatically a deep merge of its entries. Type/schema declarations do not by themselves validate the business truth of a model result or bind evidence to a Git revision. A runtime-owned result validator and explicit data projection can supply those checks. Shared state can carry execution/result and artifact references while provider-specific messages remain private; that is a feasible interface choice, not a selected schema. [State and reducers](https://docs.langchain.com/oss/python/langgraph/graph-api#state).

## Timeouts, retries and stopping work

LangGraph 1.2.11 exposes per-node `RetryPolicy`, `TimeoutPolicy` and error handlers. Exception handling is ordered: a matching retry policy runs first; the error handler runs after retries are exhausted or immediately when there is no retry. Node timeouts apply to a **single attempt**, so retrying starts a fresh timeout. They do not account for an Attempt's cumulative cost, block visits, provider attempts or Sub-agent work. [Node configuration](https://docs.langchain.com/oss/python/langgraph/graph-api-nodes), [pinned policy types](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/types.py#L418).

Per-node timeouts support async nodes only; sync nodes configured with a timeout are refused. Cancellation is cooperative, so blocking the async event loop delays it. Moving a synchronous call into a thread does not create a mechanism to kill that thread or an external subprocess. The current provider interface and its retry helper use synchronous `invoke`, and the current graph is invoked synchronously. Thus copying a YAML timeout into `add_node(timeout=...)` is not an implementation of reliable block interruption for the existing execution path. [Pinned timeout guard](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/_internal/_timeout.py), [pinned async cancellation implementation](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/pregel/_retry.py#L422), [current provider retry](https://github.com/lbacik/coding-agent/blob/815de8c3358e0d02b1f84260ab91c78b79b7f931/src/coding_agent/provider/retry.py).

Implementation implications for a later decision:

- Define which stop conditions are observed between requests/tools and which require actual in-flight cancellation or process-group termination. A clock check and interrupting execution are different guarantees.
- Do not turn a global budget/cancellation stop into an exception that generic retries automatically repeat. A block-limit result can instead become a runtime-authored routed event; an unexpected exception can follow the agreed failure policy.
- Decide the retry boundary before configuring retries. Wrapping a complete agent block can repeat model spend, workspace edits and tool calls; the existing provider helper already retries individual transient provider requests.
- Record or reserve usage outside updates that a failed node can discard. Framework rollback of graph writes cannot undo billed requests or recover missing provider usage.

These are obligations exposed by framework behavior, not decisions to change the Worker to async or to choose one retry strategy.

## External effects and durable recovery

Retries re-execute a node's body. A graph checkpoint cannot make an external write atomic with that node's return: an API may commit before the process loses the acknowledgement. The application needs a stable durable operation identity and API deduplication or read-back reconciliation. Failed/timed-out graph writes being discarded does not undo file changes, commits or published comments. [Fault tolerance and idempotency](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#retry-boundaries-and-idempotency).

Checkpointers persist graph execution state; stores persist application-defined cross-run data. Neither is mandatory to compile or execute the graph. A checkpointer introduces resume/re-execution semantics that must be considered separately from declarative graph construction. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence).

The current accepted policy gives the Run Ledger sole durable authority and makes restart finish recorded outcomes or classify unfinished work without model resumption. A configurable block graph can retain this policy: execution records/effects remain in the ledger and the compiler still uses `checkpointer=None`. Resuming an arbitrary interrupted block would be a different product decision and would require amending the recovery contract; it is not necessary to support configurable START, routing or bounded cycles. [ADR 0017](https://github.com/lbacik/coding-agent/blob/815de8c3358e0d02b1f84260ab91c78b79b7f931/docs/adr/0017-recovery-finishes-a-recorded-outcome-from-the-run-ledger.md), [effect intents and receipts](https://github.com/lbacik/coding-agent/blob/815de8c3358e0d02b1f84260ab91c78b79b7f931/src/coding_agent/ledger/store.py).

## Handoff to the human decision tickets

The framework supports the required first-release topology without code generation or an automatic persistence-policy change. The unresolved product decisions are: block/result/data interfaces; event coverage and terminal semantics; definition and scope of visits/limits; cancellation/retry boundaries; evidence and external-operation admission; durable execution identities; and recovery before/after an effect intent. The existing guarantees remain the baseline until those tickets explicitly retain or replace them.

No additional research blocker was identified. A later owner-reviewed YAML prototype should cover missing routes, an unreachable declaration, a cycle without a product limit, an unexpected result, a block limit that routes to AI-assisted Handoff, a global stop that forbids another model call and a crash after an external effect but before its receipt. Those scenarios test the product compiler/executor contract, rather than merely proving that LangGraph can compile a diagram.
